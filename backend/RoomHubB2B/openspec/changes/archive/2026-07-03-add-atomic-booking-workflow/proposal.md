## Why

RoomHub уже показывает опубликованные площадки и их занятые интервалы, но не позволяет провести аренду от заявки до завершения. Нужен управляемый процесс бронирования, который запрещает недопустимые переходы статуса и не допускает двойного резервирования одного временного интервала при конкурентных запросах.

## What Changes

- Добавить сделку бронирования с состояниями `REQUESTED`, `AWAITING_CONFIRMATION`, `CONFIRMED`, `IN_PROGRESS`, `COMPLETED`, `REJECTED`, `CANCELLED` и `EXPIRED`.
- Добавить команды создания и чтения бронирования, одобрения, отклонения, подтверждения и отмены. Произвольная запись поля `status` через CRUD API не предоставляется.
- Связать booking с организацией арендатора из проверенного JWT, а listing — с организацией арендодателя; не принимать идентификаторы участников из request body.
- Разрешить создание, подтверждение и отмену только арендатору-участнику, а одобрение и отклонение — только арендодателю-владельцу объявления. Чтение booking и истории доступно только двум организациям-участникам.
- При одобрении атомарно резервировать почасовой полуоткрытый интервал `[startAt, endAt)`. Пересекающиеся заявки могут существовать одновременно, но только первая успешно одобренная заявка получает слот; остальные получают конфликт.
- Автоматически переводить неподтверждённое одобренное бронирование в `EXPIRED` после срока подтверждения и освобождать его интервал.
- Автоматически переводить подтверждённую сделку в `IN_PROGRESS` при наступлении `startAt` и в `COMPLETED` при наступлении `endAt`.
- Фиксировать почасовую ставку и итоговую стоимость в момент создания заявки, чтобы последующее изменение объявления не меняло условия сделки.
- Записывать историю каждого успешного перехода состояния.
- Включать активные резервы сделок в существующую выдачу занятых интервалов площадки.

Пример создания заявки:

```http
POST /api/bookings
Authorization: Bearer <tenant-access-token>
Content-Type: application/json

{
  "listingId": 42,
  "startAt": "2026-07-10T10:00",
  "endAt": "2026-07-10T13:00"
}
```

```json
{
  "id": 81,
  "listingId": 42,
  "status": "REQUESTED",
  "startAt": "2026-07-10T10:00",
  "endAt": "2026-07-10T13:00",
  "pricePerHour": 2500.00,
  "totalPrice": 7500.00,
  "confirmationDeadline": null
}
```

Пример одобрения с удержанием слота:

```http
POST /api/bookings/81/approve
Authorization: Bearer <landlord-access-token>
```

```json
{
  "id": 81,
  "status": "AWAITING_CONFIRMATION",
  "confirmationDeadline": "2026-07-01T18:30:00"
}
```

## Capabilities

### New Capabilities

- `booking-workflow`: Создание сделок между аутентифицированными организациями, проверка ролей и ownership, разрешённые переходы конечного автомата, атомарное удержание и освобождение интервалов, автоматические временные переходы, расчёт стоимости и история статусов.

### Modified Capabilities

Отсутствуют. Основная директория `openspec/specs` пока не содержит синхронизированной capability календаря; интеграция сделок с текущим availability API описывается в новой capability.

## Impact

- API: новые защищённые endpoints `/api/bookings` и командные endpoints `/api/bookings/{bookingId}/...`; существующие JSON-контракты `/api/listings` и `/api/listings/{listingId}/availability` не меняются.
- База данных: новая миграция `V7`, новые таблицы бронирований и истории переходов, внутренняя ownership-связь listing с организацией арендодателя; `listing_unavailability_periods` расширяется ссылкой на бронирование и типом блокировки.
- Backend: новый доменный модуль booking, использование текущего JWT principal и ролей `LANDLORD`/`TENANT`, проверки организации-участника, транзакционные команды переходов, плановая обработка просроченных и наступивших сделок, интеграция с listing availability.
- OpenAPI: экспортируемый контракт дополняется защищёнными booking-операциями, bearer security requirement и схемами ошибок `401/403/404/409`.
- Frontend: существующие экраны не ломаются; новые операции требуют отдельного интерфейса оформления и обработки заявок.
- `ListingResponseDto` сохраняет текущие поля `id`, `title`, `city`, `pricePerHour`, `capacity`, `spaceType`, `imageUrl`, `description`, `address`; внутренний `ownerOrganizationId` в публичный каталог не добавляется.
- Внешняя оплата, создание и управление объявлениями, назначение владельца существующим seed-объявлениям через публичный API и документооборот не входят в этот MVP.
