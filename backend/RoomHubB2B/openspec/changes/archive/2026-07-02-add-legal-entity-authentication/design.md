## Context

RoomHub пока не использует Spring Security и не хранит организации или учетные записи. Каталог и календарь являются публичными read-only API, а параллельное изменение `add-atomic-booking-workflow` проектирует команды бронирования без проверки участников. Новая capability должна дать стабильную идентичность организации и роль для последующей привязки объявлений и сделок, не связывая реализацию с внешним реестром юридических лиц.

Изменение затрагивает REST API, PostgreSQL, Flyway, Spring Security, конфигурацию секретов и экспорт OpenAPI. Для MVP одна регистрация создает одну организацию и одного основного пользователя с одной неизменяемой ролью.

## Goals / Non-Goals

**Goals:**

- Регистрировать только учетные записи с реквизитами российского юридического лица: полным наименованием и 10-значным ИНН.
- Поддержать роли `LANDLORD` и `TENANT`, выбранные при регистрации.
- Атомарно создавать организацию и ее основного пользователя.
- Безопасно проверять email/пароль и выдавать короткоживущий подписанный bearer access token.
- Позволить аутентифицированному пользователю получить собственный профиль.
- Сохранить публичный доступ к каталогу, availability, OpenAPI и auth endpoints.
- Сформировать базовый deny-by-default security policy для будущих бизнес-endpoints.

**Non-Goals:**

- Проверка ИНН и организации через ФНС, ЕГРЮЛ или другой внешний источник.
- Проверка контрольных цифр ИНН; в MVP проверяется только формат из 10 цифр и уникальность.
- Подтверждение email, восстановление и смена пароля.
- Refresh token, server-side logout, отзыв отдельных access tokens и список активных сессий.
- Несколько пользователей или несколько ролей в одной организации, приглашения сотрудников и смена роли.
- Привязка существующих seed-объявлений к арендодателю и детальная авторизация booking-команд; это отдельная миграция бизнес-данных и capability.

## Decisions

### 1. Организация и пользователь хранятся отдельно

Таблица `organizations` хранит `id`, `legal_name`, `tax_id`, `created_at`; таблица `users` хранит `id`, `organization_id`, `email`, `email_normalized`, `password_hash`, `role`, `created_at`. `tax_id` и `email_normalized` имеют уникальные ограничения, `organization_id` является обязательным уникальным FK, поэтому в MVP у организации ровно один основной пользователь.

Разделение не смешивает реквизиты контрагента с учетными данными и позволяет позднее добавить сотрудников без переноса организации. Единая таблица отклонена: она проще сейчас, но затрудняет будущие связи listings/bookings с юридическим лицом, а не с конкретным логином.

Регистрация создает обе строки в одной транзакции. Конфликты уникальных ограничений преобразуются в `409 Conflict`, включая гонку двух одновременных регистраций.

### 2. Признак юридического лица определяется обязательными реквизитами

API требует непустое полное наименование и `taxId`, соответствующий `^[0-9]{10}$`. Двенадцатизначный ИНН ИП/физического лица не принимается. Backend не вызывает внешние сервисы и не утверждает, что организация реально существует.

Альтернатива с произвольным регистрационным номером отклонена, потому что текущий продукт и терминология ориентированы на российские юридические лица. ОГРН не требуется в MVP, чтобы не собирать реквизиты, которые пока не используются.

### 3. Email нормализуется, роль задается один раз

Для идентификации email обрезается по краям и приводится к lower case через locale-independent normalization; нормализованное значение используется для уникальности и входа. Исходное значение не нужно хранить отдельно. Роль является enum `LANDLORD`/`TENANT` с CHECK-ограничением базы и не изменяется публичным API.

Один пользователь с несколькими ролями отклонен для MVP: это требует отдельной модели разрешений и не нужно для описанных пользовательских потоков.

### 4. Пароль хранится только как версионированный адаптивный хеш

Используется Spring Security `DelegatingPasswordEncoder` с bcrypt и префиксом алгоритма в сохраненном значении. Каждый хеш получает случайную соль. Входной пароль имеет длину от 12 до 64 символов и дополнительно ограничивается 72 байтами UTF-8, чтобы bcrypt не обрезал значимую часть пароля.

Собственный алгоритм хеширования и быстрый SHA-256 отклонены. Пароль, request DTO и credentials исключаются из логов; API никогда не возвращает `password` или `passwordHash`.

### 5. Аутентификация stateless через короткоживущий JWT

После успешного `POST /api/auth/login` backend выпускает HMAC-SHA-256 JWT со сроком жизни 15 минут. Секрет длиной не менее 256 бит передается через конфигурацию окружения. Token содержит `sub=userId`, `organizationId`, `role`, `iat`, `exp` и `iss`; email и юридические реквизиты в token не включаются.

Spring Security resource server проверяет подпись, issuer и expiration для каждого запроса. Серверные HTTP-сессии не создаются, CSRF отключен для bearer API. `GET /api/auth/me` загружает актуальный профиль из БД по `sub`, а не доверяет token для отображаемых реквизитов.

Серверная session cookie отклонена из-за дополнительной CSRF/CORS-семантики для REST frontend. Refresh token отклонен для MVP; после истечения access token пользователь входит повторно. Ротация секрета завершает все ранее выданные сессии и служит аварийным глобальным отзывом.

### 6. Security policy строится по allowlist

Без token доступны только:

- `POST /api/auth/register`;
- `POST /api/auth/login`;
- `GET /api/listings`;
- `GET /api/listings/{listingId}/availability`;
- `GET /api/openapi` и инфраструктурные endpoints, явно разрешенные конфигурацией.

`GET /api/auth/me` и все остальные application endpoints требуют аутентификации. Разграничение конкретных listing/booking-команд по владельцу будет добавлено вместе с ownership-связями; наличие claim `role` само по себе не дает доступа к чужому ресурсу.

### 7. Ошибки имеют стабильный JSON-контракт

Validation errors возвращают `400`, конфликт нормализованного email или ИНН — `409`, неверная пара email/пароль, отсутствующий, просроченный или поврежденный token — `401`, недостаточная роль — `403`. Неверный email и неверный пароль дают одинаковое сообщение и статус, чтобы не раскрывать наличие учетной записи. Формат строится на Spring `ProblemDetail` и документируется в OpenAPI.

## Risks / Trade-offs

- [Украденный stateless token действует до истечения срока] -> Использовать 15-минутный TTL, TLS и не помещать чувствительные реквизиты в claims; отзыв и refresh rotation вынести в следующее изменение.
- [HMAC-секрет может оказаться слабым или попасть в репозиторий] -> Валидировать минимальную длину при старте, получать секрет только из окружения и не задавать production default.
- [Форматный ИНН не доказывает существование организации] -> Явно не показывать статус "проверено" и предусмотреть будущий verification status без изменения идентификатора организации.
- [Уникальный ИНН запрещает вторую самостоятельную регистрацию той же организации] -> Для MVP это защищает от дублей; сотрудники и восстановление контроля потребуют отдельного invitation/admin flow.
- [Одна роль не покрывает организацию, которая одновременно сдает и арендует] -> Сохранить роль как отдельное поле модели и спроектировать multi-role migration отдельно после появления такого сценария.
- [Deny-by-default может закрыть новый endpoint, если разработчик забудет allowlist] -> Покрыть публичные и закрытые маршруты security integration tests; это предпочтительнее случайной публикации endpoint.
- [Активное изменение booking пока не содержит ownership] -> Не заявлять в этом change защиту конкретных booking-команд; использовать созданные organization/user identifiers в последующем delta change.

## Migration Plan

1. Добавить зависимости Spring Security resource server/JOSE и конфигурационные свойства token issuer, TTL и signing secret.
2. Flyway создает `organizations` и `users` с FK, unique и CHECK-ограничениями; существующие listings и availability не изменяются.
3. Развернуть backend с обязательным signing secret и новыми auth endpoints. Поскольку текущие бизнес-endpoints входят в allowlist, существующий frontend продолжает работать.
4. Экспортировать OpenAPI и передать frontend новые schemas и bearer security scheme.
5. Rollback приложения возможен без удаления новых таблиц: предыдущая версия их игнорирует. Миграция остается forward-only; удаление учетных данных требует отдельной согласованной операции.

## Open Questions

- При добавлении нескольких сотрудников потребуется определить, кто подтверждает присоединение к организации с уже зарегистрированным ИНН.
- Перед production-развертыванием нужно выбрать способ хранения signing secret и процедуру его ротации для окружения проекта.
- Детальная матрица разрешений listings/bookings должна быть зафиксирована после появления ownership полей и не выводиться только из роли пользователя.
